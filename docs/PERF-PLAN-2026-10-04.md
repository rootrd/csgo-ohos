# 流畅化与显存压降规划（2026-10-04）

> 目标一句话：**把 de_dust2 从 ~1fps 修到"主菜单 55+ fps、进图 45+ fps"，同时显存压到 ≤1.2GB、长期 ≤1.0GB。**
> 现状：能进图能渲染（07:23 里程碑已达成），但实测 ~1fps，设备内存吃紧，属"幻灯片"级。

---

## 0. 【已定案】1fps 根因：材质系统异步渲染作业等待（2026-10-04 晚，hiperf 实锤）

### 证据链（全部本机实测）
1. 帧间隔精确 ~0.99–1.00 秒/帧（HostStateFrame 时间戳差），进程 CPU **117%**——不是"渲染慢"，是每秒烧掉一整核在**自旋等待**。
2. 逐线程 CPU：**SDL_main（游戏主循环线程）单核 100% 燃烧**，状态 R（running，用户态，无 syscall）；其余线程基本空闲。
3. **hiperf 6 秒采样（5630 样本）**平坦报告：
   `usleep 71.5% / pthread_cond_timedwait 7.3% / gettimeofday 4.5% / pthread_mutex_lock 4.0% / unlock 1.5% / clock_gettime 0.9%` —— 帧内实际工作量 <1%。
4. **hiperf 调用栈**（一条链到底）：
   ```
   SDL_main → LauncherMain → 引擎帧 (libengine_client)
     → CMaterialSystem::EndFrame()          [cmaterialsystem.cpp:4241]
        → CJob::WaitForFinish()             [jobthread.h:521]
           → CThreadPool::YieldWait(CJob**) [jobthread.cpp:632/591]
              → CThreadSyncObject::WaitForMultiple ←→ usleep 1ms 轮询自旋
   ```
5. 源码对账（`cmaterialsystem.cpp`）：
   - `mat_queue_mode` 默认 **-1**；`GetCPUInformation().m_nPhysicalProcessors >= 2` → 自动进入 **MATERIAL_QUEUED_THREADED**（cmaterialsystem.cpp:1259/1268）。
   - `EndFrame()` 在该模式下：`while (m_pActiveAsyncJob && !IsFinished()) m_pActiveAsyncJob->WaitForFinish();`（4241 行）——**每帧等一个"队列渲染作业"完成**。
   - 作业携带 **JF_QUEUE** 标志（`mat_queue_priority` 默认 1，4296-4299 行），投递到全局线程池；PC 分支不设 service thread。
   - 等待实现 `YieldWait`：先 0ms 试探取共享队列，取不到就 `TT_INFINITE` **无限轮询**；轮询体是 `WaitForMultipleObjects`（threadtools.cpp:3210）的 **1ms/事件 + usleep 死循环**。
6. 旁证：DXVK 侧完全无辜——`avgVkQueueSubmitUs ≈0.8ms`、稳态无新资源（images/buffers 计数冻结）、全日志 "compil" 仅出现 1 次（**管线编译风暴假设 H1 排除**）；`dxvk.enableAsync=True` 已生效。
7. 同一瓶颈同时解释菜单与进图的 ~1fps（该等待是每帧路径，与场景无关）。

### 结论
**每帧在 `CMaterialSystem::EndFrame()` 里等待"队列渲染作业"完成，作业被服务得极慢/唤醒延迟 ~1s，等待以 1ms 粒度轮询自旋** → 恒定 ~1fps + 100% 单核。修这个即可解锁帧率。

### 修复方案（按优先级）
| # | 方案 | 原理 | 状态 |
|---|---|---|---|
| a | **cmdline 注入 `+mat_queue_mode 0`**（同步单线程） | 直接走 `MATERIAL_SINGLE_THREADED` 分支，绕过异步作业等待 | **✅ 已验证有效（见下）** |
| b | `mat_queue_mode 1`（队列单线程）备选 | 换分支，job 由主线程自服务 | 备选 |
| c | `mat_queue_priority 0` | 去掉 JF_QUEUE，YieldWait 可自行 pop 并就地执行作业 | 备选 |
| d | 代码级根治 | 查全局线程池 worker 对 JF_QUEUE 作业的服务/唤醒为什么 ~1s 延迟（快照显示 worker 停在 `CThreadSyncObject::Wait`） | 长期项 |

### ✅ 修复验证结果（2026-10-04 晚，真机）
| 指标 | 修复前 | 修复后 |
|---|---|---|
| **主菜单帧率** | ~1.0 fps | **58.7 fps**（299 帧：平均 17.05ms，min 16.0 / max 19.0ms） |
| 进程 CPU | 117%（单核 100% 自旋） | **53.5%** |
| 游戏主循环线程 | R 态 100% 燃烧 | 正常 |

遗留（与帧率无关）：菜单 UI 渲染错位/缩小到左上角（黑底+左上角乱码条），属 Panorama UI 缩放/视口问题，另单独立项。

### 【已定界】进图场景的独立瓶颈（菜单已 59fps，进图仍 ~1fps）—— 驱动/GPU 完成信号级问题
**Present 分段账本（自加插桩 `[G9-Present]`）精确切分**（数据为前台实测，前台/后台伪影已排除）：

| 场景 | 总耗时 | 等上一帧呈现 | acquire | blit+提交 | 等帧延迟信号 | 每帧命令形态 |
|---|---|---|---|---|---|---|
| 菜单（前 64 帧） | 5.4ms | 2.2ms | 0.5ms | 2.7ms | 0.7ms | 52 绘制 / 23 通道 / 321 顶点 |
| 进图稳态 | **956ms** | 0 | 0.8ms | 0.4ms | **955ms (99.9%)** | 345 绘制 / 10-11 通道 / **321 顶点 / 34.5 万索引（≈11.5 万三角形）/ 4 次清除 8MPix** |

**消融实验链（逐步把等待"赶"到下一个位置，证明底层完成信号就是 ~1s 晚到）**：
1. 跳过帧延迟等待 → 时间原样搬到"等上一帧 present 完成"（735ms），总帧率不变。
2. 再跳过 acquire 信号量等待 → 仍在"等 present 提交完成"（735ms）。
3. present 提交完成 = 队列线程 `DxvkCommandList::synchronize()`（1s 超时的 `vkWaitForFences`）→ **GPU 侧对这批微不足道的工作的完成/信号晚到约 1 秒**。

**已系统性排除**：像素量（render=1600x717 像素减 2/3，816→841ms 无变化）、地图几何（de_shortdust 小图仅快 ~12%）、内存压力（maxtex 512→256 显存腰斩无变化）、管线编译（dxvk-shader 线程空闲、无编译日志）、交换链重建（进图期无重建）、CPU 忙（总 CPU 14%、主线程 7.8%、GPU 前端命令数正常）、清除量（4 次/帧）、acquire 信号量、帧延迟信号机制（fence 线程 10ms 轮询）、后处理链（mat_postprocess_enable 0 无效）、前台/后台状态（前台新启动复测仍 1fps）。

**结论**：进图每帧提交的 GPU 工作在驱动/内核完成路径上被延迟 ~1 秒（量级远超硬件应然；菜单同路径 5ms 说明机制本身正常）。下一步需要 GPU 时间戳查询（vkCmdWriteTimestamp）或与 DXVK fork 作者（WineHua/G9 遥测那套）对驱动侧完成延迟取证。**注意：此前"进图 246 帧/240 秒"的里程碑测量同样是这个瓶颈，与材质系统无关。**

### 附带破案 2：调试看门狗误杀进程（SIGILL 自爆）
进图轮进程在 19:01:57 死于 **SIGILL@0**；系统 faultlog（`hdc file recv` 可绕过 shell 权限读取 `/data/log/faultlog/faultlogger/`）显示崩溃线程 = `OS_FFRT_3_7`，栈顶 `_Unwind_Backtrace` —— **是我们的全线程 SIGUSR2 快照看门狗**：每 30s 对所有线程盲发信号，碰上刚 clone、TLS 未就绪的 FFRT 系统线程，处理器在残废上下文执行即崩溃。
**修复**：①看门狗默认关闭，需 `CSGO_OHOS_WATCHDOG=1` 显式开启（日常剖析改用 hiperf）；②开启时跳过 `OS_*` 系统线程。另：崩溃取证优先用系统 faultlog（faultlogger 目录，`hdc file recv` 可读）。

### 附带破案：cmdline 注入通道一直静默失效（本轮所有注入实验的元凶）
- `napi_init.cpp`（libentry）从 **`files/cmdline.txt`（浅路径）** 读注入参数 → `setenv(CSGO_OHOS_ARGS)`；该文件是 **10-02 地图二分时代的遗留 `+map|de_dust2`**，shell 写不进沙箱（EACCES），从未被覆盖。
- `engine_startup.cpp`（libmain）读 `csgo/cmdline.txt`（深路径，打包/沙箱同步维护，内容一直是对的）**却只写 debug 文件、从不赋值 `extraArgs`** —— 引擎实际始终使用 env 后备（=旧浅文件内容）。
- 结果：**近期所有 `+mat_queue_mode/+mat_pixmip/maxtex/render=` 注入全部未生效**（也解释了为何"菜单轮"总自动进图）。
- 修复：①napi 优先读深路径（浅路径仅兜底+告警）；②`engine_startup` 把深路径文件内容真正赋给 `extraArgs`（env 降为兜底）。

## 2. 根因假设（按优先级，全部设计好判定方法）

### H1 管线编译风暴 / 状态缓存失效 —— **已排除（稳态）**
判定结果：G9 账本只有 RESOURCES/SUBMIT 两类；d3d9 全日志 "compil" 字样仅 1 次；vkQueueSubmit 平均 <1ms；稳态下 images/buffers 计数冻结。管线编译不是稳态 1fps 的原因（进新场景的首次编译尖峰仍真实存在，属 P2 的预热项）。

### H2 内存压力抖动
设备只剩 1.2GB 空闲、swap 已用 4GB；我们的游戏进程 + GPU 各占 ~2GB，帧内触及被回收页 → major fault 抖动。
**判定**：清后台应用重测同一场景；观察 `top` 的 sys% 与帧率变化。若清理后显著变快即坐实。

### H3 present/旋转路径
buffer 竖屏 1276×2848 + 不做预旋转 → 合成器每帧做旋转合成；MAILBOX 模式。
**判定**：G9-Chain 的 frameUs 与 transcode 计数；配合 `CSGO_OHOS_DISPLAY=1600×717` 降分辨率对比。

### H4 GPU 慢路径 / 逐帧转码
`WineHua: comparison-sampler ...` 打印、ConvertFormat 警告（引擎给了 2 个未知格式 909529921/875844417）。
**判定**：G9-Chain 若 transcodeCalls>0 且每帧都有 → 是逐帧转码。

### H5 CPU 降频/调度
**判定**：性能模式下重测。

### H6 打点开销（先排除）
每帧一次 fprintf 到文件，量级 <1ms，不可能是 1fps 主因。**判定完成后顺手把 HostStateFrame 打点降为每 30 帧一行**。

### P0 帧级诊断 —— **已完成（2026-10-04 晚）**
产出：`hiperf` 对 56283 采 6s×500Hz，平坦报告 + 调用栈直接定位到 `CMaterialSystem::EndFrame` 的异步作业等待（见第 0 节）。G9 账本（RESOURCES/SUBMIT）、enableAsync 生效、"compil≈0" 一并取证。

### P0.5 环境清理（需要用户配合，5 分钟）
关闭后台重应用（微信等）→ 目标空闲内存 ≥4GB；插电、开性能模式；作为帧率修复后的稳健性对照轮。
### P1 显存压降（1 天，帧率修复后做，互不阻塞）
1. **MaxTextureDimension 改为运行时可配**（dxvk.conf 键如 `d3d9.ohosMaxTexDim`，免重建扫档位）。
2. 快扫 512 / 384 / 256 三档 → 记录 GL 内存 + 画质（截图留档），定运行档位。
3. **buffers 692MB/18700 个**专项剖析：给 G9 资源行加"缓冲直方图"（>256KB 的个数/总量）；查 1.87 万缓冲的来源（模型几何上传路径）。
4. 菜单 images（306MB）拆分：拆出 UI 大图/图集，看能否单独压。
5. **阶段验收：菜单 GL ≤600MB、进图 ≤1.2GB、无系统杀**。
### P2 帧率修复（进行中）
- **主修复（验证中）**：`+mat_queue_mode 0` 注入 → 预期帧率立刻从 ~1fps 释放到两位数（先看菜单，再进图）。

  - 若 a 有副作用（单线程材质系统在进图场景掉帧）：退 b/c（`mat_queue_mode 1` / `mat_queue_priority 0`），仍不行走 d（代码级：修 worker 对 JF_QUEUE 作业的服务延迟）。

- 进新场景管线编译尖峰（H1 遗留）：接通状态缓存预热/落盘命中，避免首次进图卡顿。
### P3 结构化优化（后续，1~2 周，独立排期）
- ASTC/移动压缩纹理管线（对齐 CS:NO 0.3.0：DXT→ASTC、ATI1/2→R8/RG8、转换缓存）→ 贴图上限回到 1024/2048、GL ≤800MB。
